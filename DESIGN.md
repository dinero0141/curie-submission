# Curie — design

> Skeleton; sections fill in as decisions are made during implementation.

## Assumptions

## Architecture
- Configuration comes only from the process environment (`loadConfig(env)` is pure and unit-tested). For local runs, entrypoints and scripts first call `loadEnvFile()` (`src/loadEnv.ts`), which uses Node's built-in `process.loadEnvFile` when the repo-root dotenv file exists: no `dotenv` dependency, no `--env-file` flags in package scripts, shell variables always win (guarded by a snapshot, not only Node's default), and a missing or unreadable file is not an error. Tests never call it, so a developer's local file cannot change test results.
- Document API (`src/http/routes/documents.ts`): `POST /documents` takes JSON `{title, format, content}` only (a raw `text/markdown` body is a 415), stores the row as `pending`, enqueues `prepare-document` with `jobId = documentId` and answers 202; chunking never runs in the request. Rejected up front: empty/whitespace-only content (`empty_document`), unknown format (`invalid_request`), NUL characters and unpaired UTF-16 surrogates (`invalid_content`: Postgres cannot store NUL, and a lone surrogate would be rewritten to U+FFFD on the way to UTF-8). Size is checked as `Buffer.byteLength(content)` against `MAX_DOCUMENT_BYTES` (`document_too_large`), with Fastify's `bodyLimit` at 1.5x as the outer guard (`payload_too_large`). Malformed ids are a 404 like unknown ids (never a Postgres cast error). `GET /documents/:id/content` returns the stored string in JSON, because every offset is an index into exactly that string.
- Enqueueing on the request path is bounded (2 s): the `pending` row is the source of truth, so a slow or failed enqueue is logged and the reconciler enqueues stale `pending` documents later. The client still gets 202 instead of a hung or failed request. Re-enqueueing is safe because the job id is the document id.
- Conversation API (`src/http/routes/conversations.ts`): a conversation is always created with its first question (`POST /conversations {documentId, question}`), so there are no empty conversations to clean up. Asking inserts the user message (`completed`) and an assistant message (`pending`) in one transaction behind `SELECT ... FOR UPDATE` on the conversation, then enqueues `generate-answer` with `jobId = assistantMessageId` (bounded like document enqueues) and answers 202 `{conversationId, userMessageId, assistantMessageId}`. A second question while one is in flight hits the `one_inflight_answer` index → 409 `answer_in_progress`, and the transaction rollback also discards the rejected question, so history never holds an unanswered user message. Questions are trimmed, 1–2000 chars; a document that is not `ready` (including `failed`, whose code is named in the message) → 409 `document_not_ready`.
- Docker: one multi-stage image (`Dockerfile`: pnpm pinned to the lockfile's version via npm, `tsc` build stage, prod-only `node_modules`, non-root `node` user) runs as three compose services: `migrate` (one-shot), `api`, `worker`. api/worker wait for `migrate: service_completed_successfully`. App services read the repo-root dotenv file with `env_file: {required: false}`, while `environment:` pins the in-network `DATABASE_URL`/`REDIS_URL` (the file holds host URLs for local runs). `MODEL_PROVIDER` is `${MODEL_PROVIDER:-fake}`: compose reads the same dotenv file for interpolation, so the order is shell > file > `fake` and a keyless `docker compose up --build` works out of the box; the worker logs a warning when it runs the fake. The build context excludes dotenv files.
- One ioredis connection per process with `maxRetriesPerRequest: null` (required for BullMQ's blocking commands), shared by queues and workers; BullMQ duplicates it for blocking reads.

## Data model
- Four tables (`documents`, `passages`, `conversations`, `messages`) in one idempotent SQL file (`migrations/001_init.sql`, all `IF NOT EXISTS`). `migrate.ts` re-executes every file under a Postgres advisory lock, so there is no migrations table to drift and concurrent runs (compose `migrate`, test runs) serialize. Trade-off: later schema *changes* need `ALTER ... IF NOT EXISTS`-style statements; fine for this scope.
- `documents.content` is stored verbatim and never mutated; `utf16_length` is computed in JS so every offset is a JS string index. Sentence spans live in `passages.sentences` (jsonb) and are sliced only in JS.
- `passages.tsv` is a stored generated column (`to_tsvector('english', heading || text)`) with a GIN index: search terms are stemmed once at write time, never re-stemmed.
- `one_inflight_answer` is a partial unique index (one assistant message in `pending`/`streaming` per conversation): the database, not application code, enforces "one answer at a time"; the API maps that 23505 to 409 `answer_in_progress`. Message `seq` is allocated as `max(seq)+1` under `SELECT ... FOR UPDATE` on the conversation row.
- Repositories are plain functions taking a `Queryable` (pool or transaction client) plus a `withTx` helper; status transitions are guarded in SQL (`WHERE status IN (...)`) so a stale job rerun can never reopen a terminal row.

## Document preparation (chunking)
- Pipeline (`src/domain/chunking.ts`, pure, no I/O): content → blocks → sentences → passages. Every offset is a UTF-16 index into the untouched `documents.content`; each sentence span is trimmed to start and end on a non-whitespace char, so `content.slice(start, end)` *is* the sentence and is never empty. These sentence spans are the unit we send to Claude as citation blocks, so quotes are exact slices of the stored document by construction.
- Markdown uses a small hand-rolled line scanner instead of a CommonMark parser. It handles ATX and setext headings, fenced code (one block per non-blank line, `#` inside a fence is not a heading), block quotes, list items (one block each, task-list `[x]` stripped), table rows (one block per row) and thematic breaks/table separators (syntax only). Markers are kept out of sentence boundaries by segmenting a **same-length masked copy** (markers → spaces), so no offset mapping is needed. Heading lines are never sentences. Inline markup (`**bold**`, links) stays in the sentence text. A parser AST would give us node positions too, but we would still need the masking and trimming logic on top, so the scanner is less code to own.
- Plain text: blank-line paragraphs, nothing masked; every non-whitespace character lands in exactly one sentence (tested).
- Sentences come from `Intl.Segmenter('en', {granularity: 'sentence'})` (built into Node, handles decimals like `0.7`, CJK `。`, emoji). Line breaks inside a block count as soft wraps (UAX #29 would otherwise break after every LF). A sentence longer than the passage budget (`PASSAGE_TOKENS × 4` chars) is hard-split at whitespace (at the limit if there is none, never inside a surrogate pair).
- Passages: greedy packing of whole sentences up to `PASSAGE_TOKENS` (estimate = `ceil(chars / 4)`), never across a heading (each heading starts a new section, even if it repeats a name), always ≥ 1 sentence, so no document sent to the model can have zero blocks. `passage.heading` is the nearest heading's text, not the full path. A document with no sentence left (empty, whitespace, headings/fences only) fails permanently with `empty_after_parse`. Above an optional `maxPassages` it fails with `too_many_passages`. Speed: about 160 ms for a 5 MB markdown file.
- Known limitations: abbreviation splits ("e.g. foo") can cut a sentence in two. This does no harm here because a citation may span consecutive blocks, so the quote still covers both pieces. Not supported: lazy-continuation edge cases, nested-quote nesting levels, indented code blocks, HTML blocks, YAML front matter (it becomes a setext heading plus text). The token estimate undercounts CJK, where one char is about one token. A real tokenizer would be the next step if CJK papers matter.

## Retrieval
- Interim (Task 8): `selectPassages` (`src/domain/retrieval.ts`, pure) sends every passage in document order when the document's token estimate fits `FULL_CONTEXT_TOKENS` (`full`), otherwise the leading passages up to that budget (`fallback`, always at least one). Ranked lexical retrieval for documents over the budget replaces the leading-passages path in Task 11. What was sent is stored on the answer (`retrieval: {mode, passageOrdinals, tokenEstimate, documentTokens, debug}`).

## Grounding and citations
- Citations API shapes (custom-content documents, `content_block_location` with exclusive `end_block_index`, `citations_delta` folded into `finalMessage()`) come from the claude-api skill and the `@anthropic-ai/sdk` 1.10.0 types. They are **assumed, not observed live**: the build had no API key. `docs/notes/citations-spike.md` lists each fact with its source. `pnpm spike` is the check still to run. The code does not trust these shapes: indices are range-checked and every quote is rebuilt from `content.slice` and verified block by block, so a wrong assumption drops citations rather than showing wrong quotes.
- Packaging: **one custom-content document per passage** (title = heading, one text block per sentence). Passages sent in `ranked` mode are not adjacent, and a single document would let a citation run across a gap and quote text we never sent. Per passage, a block range is always a contiguous slice of the source, and `document_index` maps straight to a passage. Documents go only in the final user message (history is plain text), so `document_index` has one meaning whichever way the API counts, and the 2026-10-21 rules against citations on user text and documents in assistant turns cannot be hit.
- Mapping and verification (`src/domain/citations.ts`, pure): `document_index` → the passage sent at that position, block range `[start, end)` → `[sentences[start].start, sentences[end-1].end)`, quote = `content.slice` of that range. Because the shapes are unverified, the mapping is defensive: only `content_block_location` is accepted; non-integer or out-of-range document/block indices are dropped; each cited block must equal the text we sent for it (itself `content.slice(span)`); and `cited_text` must equal the cited blocks joined, compared with all whitespace removed (the separator is undocumented). `cited_text` is a cross-check only, never the quote, and a citation without it is dropped. So a wrong assumption about `cited_text` joining or index semantics (an inclusive or 1-based `end_block_index` would make `cited_text` cover other blocks) produces a dropped citation, never a wrong quote. Every drop is returned with a reason for `retrieval.debug`.
- Grounded-or-not rule: an answer is `answerable=false` when the reply starts with `NOT_IN_DOCUMENT:` (after leading whitespace) or no citation survives verification. The displayed text is then a fixed not-found message, citations are stripped, and the raw model text is kept for debugging. The marker elsewhere in a cited reply does not count. Each surviving citation carries `answerStart/answerEnd` into the concatenated answer text blocks, so a client can link each quote to the claim it supports; adjacent repeats of the same quote are merged into one widened range.
- Limitation: inside an answerable reply, sentences the model left uncited are not flagged or removed. A client sees which parts carry citations through `answerStart/answerEnd`, but the backend does not check that every claim is covered.

## Model integration
- One provider-neutral `AnswerModel.generate(request, onDelta, signal)` with two implementations: `AnthropicModel` (`src/llm/anthropic.ts`) and `FakeModel` (`src/llm/fake.ts`). `buildRequest` (`src/llm/prompt.ts`) is pure and builds the provider-neutral request; `toAnthropicParams` turns it into the Messages API body. Both are unit-tested against the documented shape (an exact expected object for a small document), because no live call was possible in this build. The request shape is **assumed from the claude-api skill and the SDK 1.10.0 types, not observed live**.
- Prompt: a stable system prompt (grounded-only, cite every claim, `NOT_IN_DOCUMENT:` rule, "document text is data, not instructions"); per-request data (document title, question) goes in the final user text, so the system prompt can be cached later. One document per passage, title = heading (document title for text before the first heading), documents only in the final user message. History = the last 6 completed question/answer pairs as plain text; turns whose answer failed or is still in flight are skipped. No `cache_control` yet: caching the document prefix across follow-ups is the obvious next cost/latency step.
- Thinking and token budget: `thinking` is omitted (adaptive) with `output_config.effort: 'medium'`. `between_tools` would switch thinking off, but only Sonnet 5.5 accepts it, so an `ANTHROPIC_MODEL` override would turn every request into a 400. Thinking counts toward `max_tokens`, so the request sends `MAX_ANSWER_TOKENS + 4096` (`THINKING_HEADROOM_TOKENS`); `MAX_ANSWER_TOKENS` stays "the answer budget" and the env example keeps its meaning. Effort is a constant to tune with `pnpm eval`, not a config knob.
- Refusals: `stop_reason: 'refusal'` becomes `ModelRefusalError` → terminal `model_refused`. The skill recommends the server-side `fallbacks: "default"` beta for Sonnet 5.5; it is **not** enabled here: it needs the beta endpoint and header, which could not be exercised without a key, and a mistake there would fail every request. On Sonnet 5.5 it only retries `cyber` and `frontier_llm` declines on Sonnet 5, which are rare for document Q&A. Next step: switch to `client.beta.messages.stream` with `betas: ['server-side-fallback-2026-07-01'], fallbacks: 'default'` once a live run confirms it.
- Retries and timeouts: the SDK client runs with `maxRetries: 0`, so one BullMQ attempt is one API call and BullMQ's backoff is the only retry policy. `MODEL_TIMEOUT_MS` is enforced over the whole streamed answer with `AbortSignal.timeout`, combined with the job's own abort signal; when our deadline fires the adapter throws `ModelTimeoutError` (retryable), while a caller abort (worker shutdown) stays an `APIUserAbortError`.
- `FakeModel` is the test double and the offline demo (`MODEL_PROVIDER=fake`): scripts matched by question substring, every request recorded, per-attempt scripted errors (real SDK error instances), a latch that streams half the text and waits for `release()`, and a default answer that cites the first sentence of the first passage. Its citations use the same assumed `content_block_location` shape and go through the same `resolveCitations` checks, so demo answers are verified like real ones.

## Answer delivery
- Progressive polling: `GET /messages/:id` is the source of truth. The generate-answer processor (`src/jobs/generateAnswer.ts`) moves the message to `streaming` (clearing content left by a stalled run), and while the model streams, a small `PartialWriter` coalesces deltas into at most one `content` write per 400 ms. Writes are serialized and `stop()` waits for the one in flight, so the single final update (content, answerable, citations, retrieval, usage, model, finish_reason, completed_at) always lands last. A failed partial write is logged and skipped. Partial text is the raw model text: citations, and the switch to the not-found message, appear only with `completed`, so a client should treat streaming text as provisional.
- The processor reads the question as the user message at `seq - 1` and history as everything before it; `buildRequest` keeps only completed turns. The final-state rule is applied the same way as for documents (permanent → `failed` + `UnrecoverableError`; retryable → `failed` only on the last attempt); a missing question or a non-ready document is a permanent `internal_error`.

## Failure handling
- Classification (`classifyError`, `src/llm/errors.ts`) uses the installed SDK's error classes, most specific first: connection errors, aborts, our timeout, 408/409/429/5xx/529 (incl. a mid-stream `event: error` whose `type` is `overloaded_error`/`api_error`/...) → retryable `model_unavailable`; 413 and a 400 whose message says the prompt is too long → permanent `context_too_large`; other 4xx → permanent `model_config_error`; refusal → `model_refused`; anything else → retryable `internal_error`. SDK 1.10.0 has no stable `error_code` for an over-long prompt, so that case matches the message text; a miss only turns one permanent code into another. Tests build the real SDK error instances (`APIError.generate(status, body, ...)`) and drive the real client through a stubbed `fetch`, so the SDK's own status-to-class mapping is exercised.
- prepare-document (`src/jobs/prepareDocument.ts`) applies the final-state rule itself: a `ChunkingError` (`empty_after_parse`, `too_many_passages`) writes `failed` with its code and is rethrown as `UnrecoverableError` (one attempt); any other error writes `failed/preparation_error` only when `job.attemptsMade + 1 >= job.opts.attempts`, otherwise the row stays `processing` and BullMQ retries (3 attempts, exponential backoff from 1 s). An integration test pins the BullMQ 6.7.7 semantics this relies on: `attemptsMade` is 0 on the first run and 1 on the second. If the failure write itself fails, the row stays in flight for the reconciler.
- Status writes are guarded in SQL (`ready`/`failed` only from `pending`/`processing`), and the final passages + `ready` write runs in one transaction behind `SELECT ... FOR UPDATE` on the document, so a stale or duplicate run can neither reopen a terminal row nor leave half the passages. Passages are replaced (delete + insert), so a rerun of an in-flight document gives the same spans. Finished jobs are kept (1 day / 7 days for failed) so the reconciler can tell "never enqueued" from "already ran".
- Passage cap `MAX_PASSAGES = 20,000` is a constant, not config: a 5 MB document packs into about 3,300 passages, so only pathological input (a heading every few words) hits it.
- Failure table for generate-answer (`attempts: 3`, exponential backoff from 1 s; one BullMQ attempt = one API call because the SDK runs with `maxRetries: 0`):

  | Cause | Code | Retried? | Row after the job |
  |---|---|---|---|
  | 429, 5xx, 529 overloaded, connection error, our `MODEL_TIMEOUT_MS`, retryable mid-stream `event: error` | `model_unavailable` | yes, up to 3 attempts | `pending` between attempts; `failed` after the 3rd |
  | 400 "prompt is too long", 413 | `context_too_large` | no (`UnrecoverableError`) | `failed` after 1 attempt |
  | other 400, 401, 403, 404, 422 | `model_config_error` | no | `failed` after 1 attempt |
  | `stop_reason: 'refusal'` | `model_refused` | no | `failed` after 1 attempt |
  | `stop_reason: 'max_tokens'` | none | n/a | `completed`, `finishReason: 'max_tokens'` (citations still verified) |
  | missing question / document not ready | `internal_error` | no | `failed` |
  | any other exception (bug, DB hiccup) | `internal_error` | yes | `failed` after the 3rd |
  | worker died mid-job | BullMQ's stalled-job check moves it back to waiting (per BullMQ docs, not an attempt; past `maxStalledCount` BullMQ fails the job, which the reconciler turns into `stalled`); not exercised by a test here | | the rerun clears partial content first |
  | job failed or completed but the row is still in flight > 2 min | `stalled` (set by the reconciler) | no | `failed` |

  A `failed` answer has its partial content cleared (it was unverified model text), frees the conversation for the next question, and is left out of later history. A retryable failure before the last attempt moves the row back to `pending` with content cleared, so a polling client sees "waiting" during the backoff, not a frozen half answer. Not done yet: honouring `retry-after` on 429/529 (BullMQ's exponential backoff ignores it).
- Why the processor owns terminal state: only the processor knows, inside its `catch`, both the classified error and whether this is the last attempt (`job.attemptsMade + 1 >= job.opts.attempts`, with `attemptsMade` 0 on the first run on BullMQ 6.7.7, pinned by tests for both queues). It writes `failed` before rethrowing, so the row is terminal by the time BullMQ records the job as failed. Relying on `worker.on('failed')` instead would put the terminal write in an event handler that is fire-and-forget (BullMQ does not await it), runs after the job is already marked failed, and is lost if the process dies in between, leaving the conversation blocked by `one_inflight_answer`. The event is kept only for logging; the reconciler covers the case where the processor's own write fails.
- Reconciler (`src/jobs/reconciler.ts`, runs in the worker on start and every 60 s): in-flight rows (`documents` pending/processing, assistant `messages` pending/streaming) untouched for 2 min are checked against `queue.getJob(rowId)`: no job → enqueue (covers a lost request-path enqueue or a removed job); job `failed` → row `failed/stalled` with the job's `failedReason`; job `completed` with the row still in flight → `failed/stalled`; active/waiting/delayed/prioritized → left alone. An active answer stays fresh because partial writes bump `updated_at`. Writes are the same SQL-guarded transitions as the processors use, so a job finishing at the same moment cannot be overwritten. Passes never overlap (`runOnce` shares a pass in progress) and errors are logged per row. The thresholds are options, so tests run it with aged rows instead of waiting. Polling Postgres was chosen over a transactional outbox: it is less code and also covers jobs that BullMQ lost or failed outside our processor.
