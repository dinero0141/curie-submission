# Curie — design

Design, decisions and status of the chat-with-a-document backend. Running it: [README.md](README.md). Endpoints,
shapes, statuses and error codes: [docs/API.md](docs/API.md). Assumed Claude Citations shapes:
[docs/notes/citations-spike.md](docs/notes/citations-spike.md).

> Status: final for this build (plan Tasks 1–14). Built **without an Anthropic API key**: the real Claude API was
> never called, the Citations shapes are assumed, and `pnpm spike` / `pnpm eval` have not been run against Claude. All
> automated tests run on `FakeModel`. See [Complete vs remaining](#complete-vs-remaining) and
> [Verification](#verification).

## Assumptions
- One user, no authentication (sketch under [Access control](#access-control)).
- Input is Markdown or plain text sent as a JSON string, up to 5 MB of UTF-8. PDF is out of scope; it would be a
  converter in the prepare step that produces text under the same offset contract.
- A document is immutable after upload; a new version is a new document. That keeps every stored offset valid.
- A conversation is about exactly one document, fixed when it is created.
- "Based only on the document" means: an answer is shown as answerable only if it carries at least one quotation
  that we verified against the stored text. An answer with no verified quotation fails with `citations_unverified`;
  only the model's explicit `NOT_IN_DOCUMENT` statement produces the not-found result.
- English-language documents for retrieval quality (Postgres `english` text search, `Intl.Segmenter('en')`); other
  languages chunk correctly but are not stemmed.
- Claude (Anthropic) is the only model provider. It has no embeddings API, so retrieval is lexical.
- An answer may take seconds to tens of seconds; the client polls and sees partial text meanwhile.

## Architecture
- Overview:

  ```
  client ──HTTP──> api (Fastify) ──SQL──> Postgres: documents, passages, conversations, messages
                     │ enqueue (job id = row id)                ^
                     v                                          │ status, partial content, results
                   Redis (BullMQ: prepare-document, generate-answer)
                     │                                          │
                     v                                          │
                   worker: chunking │ passage selection │ Claude (streamed, Citations) │ verification
                     └─ reconciler (on start + every 60 s)
  ```

  The API validates, writes rows and enqueues; it never chunks or calls the model. The worker does the slow work and
  writes results to the rows the client polls. Postgres rows are the source of truth; Redis holds only jobs, so a lost
  job is recoverable from the row (reconciler).
- Configuration comes only from the process environment (`loadConfig(env)` is pure and unit-tested). For local runs, entrypoints and scripts first call `loadEnvFile()` (`src/loadEnv.ts`), which uses Node's built-in `process.loadEnvFile` when the repo-root dotenv file exists: no `dotenv` dependency, no `--env-file` flags in package scripts, shell variables always win (Node's own behaviour on Node 22, pinned by a unit test), and a missing or unreadable file is not an error. Tests never call it, so a developer's local file cannot change test results.
- Document API (`src/http/routes/documents.ts`): `POST /documents` takes JSON `{title, format, content}` only (any other content type, `text/plain` included, is a 415; Fastify's default text parser is removed), stores the row as `pending`, enqueues `prepare-document` with `jobId = documentId` and answers 202; chunking never runs in the request. Rejected up front: empty/whitespace-only content (`empty_document`), unknown format (`invalid_request`), NUL characters and unpaired UTF-16 surrogates (`invalid_content`: Postgres cannot store NUL, and a lone surrogate would be rewritten to U+FFFD on the way to UTF-8). The same check applies to `title` and `question` (`invalid_request`), so no stored text can turn into a 500. Size is checked as `Buffer.byteLength(content)` against `MAX_DOCUMENT_BYTES` (`document_too_large`), with Fastify's `bodyLimit` at 1.5x as the outer guard (`payload_too_large`). Malformed ids are a 404 like unknown ids (never a Postgres cast error). `GET /documents/:id/content` returns the stored string in JSON, because every offset is an index into exactly that string.
- Enqueueing on the request path is bounded (`ENQUEUE_TIMEOUT_MS`, 2 s): the `pending` row is the source of truth, so a slow or failed enqueue is logged and the reconciler enqueues stale `pending` documents later. The client still gets 202 instead of a hung or failed request. Re-enqueueing is safe because the job id is the document id.
- Conversation API (`src/http/routes/conversations.ts`): a conversation is always created with its first question (`POST /conversations {documentId, question}`), so there are no empty conversations to clean up. Asking inserts the user message (`completed`) and an assistant message (`pending`) in one transaction (follow-ups behind `SELECT ... FOR UPDATE` on the conversation; a new conversation is invisible to others until COMMIT, so it needs no lock), then enqueues `generate-answer` with `jobId = assistantMessageId` (bounded like document enqueues) and answers 202 `{conversationId, userMessageId, assistantMessageId}`. A second question while one is in flight hits the `one_inflight_answer` index → 409 `answer_in_progress`, and the transaction rollback also discards the rejected question, so history never holds an unanswered user message. Questions are trimmed, 1–2000 chars; a document that is not `ready` (including `failed`, whose code is named in the message) → 409 `document_not_ready`.
- Docker: one multi-stage image (`Dockerfile`: pnpm pinned to the lockfile's version via npm, `tsc` build stage, prod-only `node_modules`, non-root `node` user) runs as three compose services: `migrate` (one-shot), `api`, `worker`. api/worker wait for `migrate: service_completed_successfully`. App services read the repo-root dotenv file with `env_file: {required: false}`, while `environment:` pins the in-network `DATABASE_URL`/`REDIS_URL` (the file holds host URLs for local runs). `MODEL_PROVIDER` is `${MODEL_PROVIDER:-fake}`: compose reads the same dotenv file for interpolation, so the order is shell > file > `fake` and a keyless `docker compose up --build` works out of the box; the worker logs a warning when it runs the fake. The build context excludes dotenv files.
- One ioredis connection per process with `maxRetriesPerRequest: null` (required for BullMQ's blocking commands), shared by queues and workers; BullMQ duplicates it for blocking reads.

## Data model

| Table | Key columns | Relations |
|---|---|---|
| `documents` | `title`, `format` (`markdown`/`text`), `content` (verbatim), `utf16_length`, `status`, `failure_code`/`failure_message`, `passage_count`, `ready_at` | 1–n `passages`, 1–n `conversations` |
| `passages` | `ordinal` (unique per document), `start_offset`/`end_offset`, `heading`, `sentences` (jsonb `[{start, end}]`), `text`, `token_estimate`, `tsv` (generated) | n–1 `documents`, `ON DELETE CASCADE` |
| `conversations` | `document_id`, timestamps | n–1 `documents` (cascade), 1–n `messages` |
| `messages` | `seq` (unique per conversation), `role`, `status`, `content`, `answerable`, `citations`/`retrieval`/`usage` (jsonb), `finish_reason`, `model`, `attempts`, `error_code`/`error_message`, `completed_at` | n–1 `conversations` (cascade) |

- Citations and the retrieval record are jsonb on the assistant message, not a `citations` table: they are written once in the final update, always read with their message, and never queried on their own.
- Four tables (`documents`, `passages`, `conversations`, `messages`) in one idempotent SQL file (`migrations/001_init.sql`, all `IF NOT EXISTS`). `migrate.ts` re-executes every file under a Postgres advisory lock, so there is no migrations table to drift and concurrent runs (compose `migrate`, test runs) serialize. Trade-off: later schema *changes* need `ALTER ... IF NOT EXISTS`-style statements; fine for this scope.
- `documents.content` is stored verbatim and never mutated; `utf16_length` is computed in JS so every offset is a JS string index. Sentence spans live in `passages.sentences` (jsonb) and are sliced only in JS.
- `passages.tsv` is a stored generated column (`to_tsvector('english', coalesce(heading, '') || ' ' || text)`) with a GIN index: search terms are stemmed once at write time, never re-stemmed.
- `one_inflight_answer` is a partial unique index (one assistant message in `pending`/`streaming` per conversation): the database, not application code, enforces "one answer at a time"; the API maps that 23505 to 409 `answer_in_progress`. Message `seq` is allocated as `max(seq)+1` under `SELECT ... FOR UPDATE` on the conversation row.
- Repositories are plain functions taking a `Queryable` (pool or transaction client) plus a `withTx` helper; status transitions are guarded in SQL (`WHERE status IN (...)`) so a stale job rerun can never reopen a terminal row.

## Document preparation (chunking)
- Pipeline (`src/domain/chunking.ts`, pure, no I/O): content → blocks → sentences → passages. Every offset is a UTF-16 index into the untouched `documents.content`; each sentence span is trimmed to start and end on a non-whitespace char, so `content.slice(start, end)` *is* the sentence and is never empty. These sentence spans are the unit we send to Claude as citation blocks, so quotes are exact slices of the stored document by construction.
- Markdown uses a small hand-rolled line scanner instead of a CommonMark parser. It handles ATX and setext headings, fenced code (one block per non-blank line, `#` inside a fence is not a heading), block quotes, list items (one block each, task-list `[x]` stripped), table rows (one block per row) and thematic breaks/table separators (syntax only). Markers are kept out of sentence boundaries by segmenting a **same-length masked copy** (markers → spaces), so no offset mapping is needed. Heading lines are never sentences. Inline markup (`**bold**`, links) stays in the sentence text. The line regexes are written so they cannot backtrack super-linearly (the ATX closing sequence and table separator rows are parsed by hand): a review found the first versions quadratic on a long run of spaces, enough for one upload to block a worker for hours; a unit test chunks ~1 MB lines under a time bound. A parser AST would give us node positions too, but we would still need the masking and trimming logic on top, so the scanner is less code to own.
- Plain text: blank-line paragraphs, nothing masked; every non-whitespace character lands in exactly one sentence (tested).
- Sentences come from `Intl.Segmenter('en', {granularity: 'sentence'})` (built into Node, handles decimals like `0.7`, CJK `。`, emoji). Line breaks inside a block count as soft wraps (UAX #29 would otherwise break after every LF). A sentence longer than the passage budget (`PASSAGE_TOKENS × 4` chars) is hard-split at whitespace (at the limit if there is none, never inside a surrogate pair).
- Passages: greedy packing of whole sentences up to `PASSAGE_TOKENS` (estimate = `ceil(chars / 4)`), never across a heading (each heading starts a new section, even if it repeats a name), always ≥ 1 sentence, so no document sent to the model can have zero blocks. `passage.heading` is the nearest heading's text, not the full path, whitespace-collapsed and capped at 200 chars (`MAX_HEADING_LENGTH`, cut at a word boundary with `…`): a heading is copied into every passage of its section (row, `tsv`, and the document title of every sent passage), so one huge ATX line or setext paragraph would otherwise be multiplied by the passage count. A passage's `token_estimate` counts its heading too, so the full/ranked budget matches what is sent. A document with no sentence left (empty, whitespace, headings/fences only) fails permanently with `empty_after_parse`. Above an optional `maxPassages` it fails with `too_many_passages`. Speed: about 160 ms for a 5 MB markdown file.
- Known limitations: abbreviation splits ("e.g. foo") can cut a sentence in two. This does no harm here because a citation may span consecutive blocks, so the quote still covers both pieces. Not supported: lazy-continuation edge cases, nested-quote nesting levels, indented code blocks, HTML blocks, YAML front matter (it becomes a setext heading plus text). The token estimate undercounts CJK, where one char is about one token. A real tokenizer would be the next step if CJK papers matter.

## Retrieval
- Three modes, chosen per answer by the generate-answer processor (`retrieve` in `src/jobs/generateAnswer.ts`). The policy is pure (`src/domain/retrieval.ts`, unit-tested first); the SQL is in `src/db/search.ts`.
  - `full`: the document's summed token estimate is at most `FULL_CONTEXT_TOKENS` → every passage, in document order, no search.
  - `ranked` (Task 11): a larger document is searched. Only a light index (`id, ordinal, token_estimate`) is read to decide; the text of the selected passages is loaded afterwards by ordinal.
  - `fallback`: a larger document with nothing to search for (stopword-only question) or no hits → the leading passages up to the budget. Every mode sends at least one passage.
- Query text = current question + the previous user question in the conversation, so a follow-up like "And how long did it take?" (nearly all stop words) still carries the earlier question's terms (tested).
- OR tsquery: `to_tsquery('simple', replace(plainto_tsquery('english', q)::text, ' & ', ' | '))`, built and searched in one statement. `plainto_tsquery` parses free text safely (user tsquery syntax is just words), drops stop words and stems once; `&` → `|` because a question rarely shares every term with the right passage; re-parsing with `simple` keeps the stems (re-parsing with `english` would stem twice, `universities` → `univers` → `univ`, and miss; caught in plan review, pinned by a test). `numnode(q) = 0` → `fallback`.
- Ranking: `ts_rank_cd` (cover density) over the stored `tsvector` (GIN index), ties by document order, top 8 (`RANKED_TOP_K`).
- Selection under the budget (`FULL_CONTEXT_TOKENS` again): first the hits in rank order (the first one even if it alone is over the budget), then the ±1 neighbours of the hits that made it in, also in rank order; a passage that does not fit is skipped and smaller later ones may still be added; duplicates are dropped; the result is sent in document order. Hits come first because a neighbour only adds context, while a hit may hold the answer. With 8 hits of about 400 tokens plus 16 neighbours (about 10k tokens) the 60k budget rarely binds; tests use small budgets to exercise the cap.
- Recorded on the answer (`messages.retrieval`): `mode`, `passageIds` and `passageOrdinals` (what was sent), `hits` (`{passageId, ordinal, rank, score}`, best first, including hits cut by the budget), `tokenEstimate`, `documentTokens`, and in `debug` the searched text and tsquery. That makes "why did it answer from this passage" answerable after the fact.
- Not verified: ranked mode against the real model (all tests use `FakeModel`; the planned live eval uses only the sample, which is `full`), or on a real long paper. Non-adjacent passages are sent as separate custom-content documents, so a citation cannot span a gap between them ([citations-spike.md](docs/notes/citations-spike.md), contiguity).
- Why "whole document when it fits" first: for one selected document, the best retrieval is no retrieval. The sample (416 estimated tokens) fits easily, and so should a typical research paper of 5–15k words (roughly 30–100k characters against a 60k-token / about 240k-character budget; not yet tried with a real paper), so the model sees everything and there is no recall problem to defend. Retrieval quality only matters for long documents.
- Why lexical (Postgres full-text search) for long documents: Claude has no embeddings API, and adding a second provider plus a vector index for single-document Q&A is more moving parts than the problem needs. FTS is deterministic and explainable (we can show why a passage was chosen), lives in the database we already run, and the `tsvector` is computed once at write time. Research questions tend to reuse the document's own terms (names, metrics, dates). Its known weakness is vocabulary mismatch: a question phrased with synonyms the document does not use ranks the right passage low. Mitigations in the design: the previous question in the query, neighbour passages, generous top-k; next steps would be query expansion by a cheap model call, or hybrid lexical + embedding ranking with `pgvector` if a second provider is acceptable. Grounding does not depend on retrieval quality: a missed passage yields "not found" (or a weaker answer), never a quote from outside the document.
- Full-length papers and limits:
  - Upload: 5 MB of UTF-8 (`MAX_DOCUMENT_BYTES`), about 1.3M estimated tokens / 3,300 passages; chunking 5 MB takes about 160 ms.
  - Per question: at most `FULL_CONTEXT_TOKENS` (60k, estimated as `chars / 4`) of passages, plus the system prompt, up to 6 earlier turns as text, and `MAX_ANSWER_TOKENS + 4096` output tokens. 60k is a cost and latency choice, well below the model's context window; it can be raised by config.
  - If the API still rejects the prompt as too long, the answer fails permanently with `context_too_large`.
  - The `chars / 4` estimate undercounts CJK text (about one token per character), so a CJK document can send more tokens than the budget suggests.
  - Unknown: how many custom-content documents or blocks one request may carry (not stated in the docs or SDK types; [citations-spike.md](docs/notes/citations-spike.md) fact 15). A 60k-token document is about 150 passages, so about 150 documents and several thousand sentence blocks in one request; this is unverified. If it hits a limit, the planned fallback is one document per run of adjacent passages.

## Grounding and citations
- Citations API shapes (custom-content documents, `content_block_location` with exclusive `end_block_index`, `citations_delta` folded into `finalMessage()`) come from the claude-api skill and the `@anthropic-ai/sdk` 1.10.0 types. They are **assumed, not observed live**: the build had no API key. `docs/notes/citations-spike.md` lists each fact with its source. `pnpm spike` is the check still to run. The code does not trust these shapes: indices are range-checked, `cited_text` must match the cited blocks, and every quote is rebuilt from `content.slice`, so a wrong assumption drops citations rather than showing wrong quotes.
- Packaging: **one custom-content document per passage** (title = heading, one text block per sentence). Passages sent in `ranked` mode are not adjacent, and a single document would let a citation run across a gap and quote text we never sent. Per passage, a block range is always a contiguous slice of the source, and `document_index` maps straight to a passage. Documents go only in the final user message (history is plain text), so `document_index` has one meaning whichever way the API counts, and the 2026-10-21 rules against citations on user text and documents in assistant turns cannot be hit.
- Mapping and verification (`src/domain/citations.ts`, pure): `document_index` → the passage sent at that position, block range `[start, end)` → `[sentences[start].start, sentences[end-1].end)`, quote = `content.slice` of that range. Because the shapes are unverified, the mapping is defensive: only `content_block_location` is accepted; non-integer or out-of-range document/block indices are dropped; and `cited_text` must equal the cited blocks joined, compared with all whitespace removed (the separator is undocumented). That `cited_text` comparison is the real check on the model's output (the blocks we sent are our own `content.slice(span)`, so comparing them with our spans would test nothing); it is never the quote, and a citation without it is dropped. Remaining gap: an off-by-one index landing on an identical repeated sentence passes with the right text but that other sentence's offsets. So a wrong assumption about `cited_text` joining or index semantics (an inclusive or 1-based `end_block_index` would make `cited_text` cover other blocks) produces a dropped citation, never a wrong quote; an answer left with none fails with `citations_unverified`, never shown as "not in the document". Every drop is returned with a reason for `retrieval.debug`.
- Grounded-or-not rule: an answer is `answerable=true` if and only if it has ≥ 1 verified citation, whatever the marker says, and `answerable=false` (completed) only when no citation was verified and the reply carries the `NOT_IN_DOCUMENT:` marker. A verified citation always wins: the prompt asks both for the marker and for a cited partial answer, so a reply such as `NOT_IN_DOCUMENT: Y is not stated. X [verified citation].` stays answerable with the model text (marker included) and its quotes, rather than claiming the document lacks what was just verified against it. Detection tolerates formatting, since real-model adherence is unknown: at the start after whitespace and Markdown `*_`>#` characters, any case, followed by any non-alphanumeric (`**NOT_IN_DOCUMENT:**`, `NOT_IN_DOCUMENT -`); when the model cited nothing at all, also anywhere in the reply (after a preamble sentence). A partial answer whose citations were all dropped by verification (`X [cited]. NOT_IN_DOCUMENT: Y is not stated.`) is not reported as not-found either: it fails as `citations_unverified`, since the dropped citations show the model found relevant passages. The displayed text is then a fixed not-found message, citations are stripped, and the raw model text is kept for debugging. A reply with no verified citation and no marker is not evidence about the document, so "not found" is never claimed for it: cut by `max_tokens`, it fails with `answer_truncated`; otherwise (the model cited nothing, or every citation was dropped by verification, which is how a wrong Citations shape assumption would show up) it fails with `citations_unverified` and the worker logs a warn with each drop reason and the citation's type and keys. When retrieval was `ranked` or `fallback`, the not-found message says only the searched parts lacked the answer.
- A quote spanning several sentences is one contiguous slice of the content, so if those sentences sit in different Markdown blocks it includes the syntax between them (a list or quote marker, a table pipe row) that was masked out of what the model saw. The text is still real document text; API.md says so. The marker elsewhere in a cited reply does not count. Each surviving citation carries `answerStart/answerEnd` into the concatenated answer text blocks, so a client can link each quote to the claim it supports; adjacent repeats of the same quote are merged into one widened range.
- Limitation: inside an answerable reply, sentences the model left uncited are not flagged or removed. A client sees which parts carry citations through `answerStart/answerEnd`, but the backend does not check that every claim is covered.

## Model integration
- One provider-neutral `AnswerModel.generate(request, onDelta, signal)` with two implementations: `AnthropicModel` (`src/llm/anthropic.ts`) and `FakeModel` (`src/llm/fake.ts`). `buildRequest` (`src/llm/prompt.ts`) is pure and builds the provider-neutral request; `toAnthropicParams` turns it into the Messages API body. Both are unit-tested against the documented shape (an exact expected object for a small document), because no live call was possible in this build. The request shape is **assumed from the claude-api skill and the SDK 1.10.0 types, not observed live**.
- Prompt: a stable system prompt (grounded-only, cite every claim, `NOT_IN_DOCUMENT:` rule, "document text is data, not instructions"); per-request data (document title, question) goes in the final user text, so the system prompt can be cached later. One document per passage, title = heading (document title for text before the first heading), documents only in the final user message. History = the last 6 completed question/answer pairs as plain text; turns whose answer failed or is still in flight are skipped. No `cache_control` yet: caching the document prefix across follow-ups is the obvious next cost/latency step.
- Thinking and token budget: `thinking` is omitted (adaptive) with `output_config.effort: 'medium'`. `between_tools` would switch thinking off, but only Sonnet 5.5 accepts it, so an `ANTHROPIC_MODEL` override would turn every request into a 400. Thinking counts toward `max_tokens`, so the request sends `MAX_ANSWER_TOKENS + 4096` (`THINKING_HEADROOM_TOKENS`); `MAX_ANSWER_TOKENS` stays "the answer budget" and the env example keeps its meaning. Effort is a constant to tune with `pnpm eval`, not a config knob.
- Refusals: `stop_reason: 'refusal'` becomes `ModelRefusalError` → terminal `model_refused`. The skill recommends the server-side `fallbacks: "default"` beta for Sonnet 5.5; it is **not** enabled here: it needs the beta endpoint and header, which could not be exercised without a key, and a mistake there would fail every request. On Sonnet 5.5 it only retries `cyber` and `frontier_llm` declines on Sonnet 5, which are rare for document Q&A. Next step: switch to `client.beta.messages.stream` with `betas: ['server-side-fallback-2026-07-01'], fallbacks: 'default'` once a live run confirms it.
- Retries and timeouts: the SDK client runs with `maxRetries: 0`, so one BullMQ attempt is one API call and BullMQ's backoff is the only retry policy. `MODEL_TIMEOUT_MS` is enforced over the whole streamed answer with `AbortSignal.timeout`, combined with the job's own abort signal; when our deadline fires the adapter throws `ModelTimeoutError` (retryable), while a caller abort (worker shutdown) stays an `APIUserAbortError`.
- `FakeModel` is the test double and the offline demo (`MODEL_PROVIDER=fake`): scripts matched by question substring, every request recorded (except in the demo worker, `createAnswerModel` builds it with `{ record: false }` so a long-running worker does not keep a copy of the document per answer), per-attempt scripted errors (real SDK error instances), a latch that streams half the text and waits for `release()` (optionally failing there, `midStreamErrors`), and a default answer that cites the first sentence of the first passage. Its citations use the same assumed `content_block_location` shape and go through the same `resolveCitations` checks, so demo answers are verified like real ones.

## Answer delivery
- Progressive polling: `GET /messages/:id` is the source of truth. The generate-answer processor (`src/jobs/generateAnswer.ts`) moves the message to `streaming` (clearing content left by a stalled run), and while the model streams, a small `PartialWriter` (`src/jobs/partialWriter.ts`, unit-tested with fake timers) coalesces deltas into at most one `content` write per 400 ms. Writes are serialized and `stop()` waits for the one in flight, so the single final update (content, answerable, citations, retrieval, usage, model, finish_reason, completed_at) always lands last. A failed partial write is logged and skipped. Partial text is the raw model text: citations, and the switch to the not-found message, appear only with `completed`, so a client should treat streaming text as provisional.
- Why polling, not streaming, for now: the answer outlives any one HTTP request. With polling the client needs only `GET /messages/:id`, which works the same during generation, after a reconnect, after a worker retry and after completion, and there is no second source of truth to keep consistent with the row. The cost is latency granularity (partial text every ~400 ms plus the poll interval) and some extra GETs, which is acceptable for answers that take seconds.
- Next step, SSE (plan Task 15): skipped by the human after Task 14, because time was past the 4 h target and progressive polling already meets the "deliver while it takes time" requirement. The design: the worker also appends `start {runId}` (on every attempt, so a client drops text from a failed attempt), `delta` and, only after the DB commit, `completed`/`failed` events to a Redis Stream per message (expiry 1 h). `GET /messages/:id/events` replays from `Last-Event-ID` (or the start) with `XREAD BLOCK`, or sends one final event if the row is already terminal. Polling stays the fallback and the source of truth.
- The processor reads the question as the user message at `seq - 1` and history as everything before it; `buildRequest` keeps only completed turns. The final-state rule is applied the same way as for documents (permanent → `failed` + `UnrecoverableError`; retryable → `failed` only on the last attempt); a missing question or a non-ready document is a permanent `internal_error`. An `internal_error` row stores a generic message; the original error (which can name SQL relations or constraints) is only logged.

## Failure handling
- Classification (`classifyError`, `src/llm/errors.ts`) uses the installed SDK's error classes, most specific first: connection errors, aborts, our timeout, 408/409/429/5xx/529 (incl. a mid-stream `event: error` whose `type` is `overloaded_error`/`api_error`/...) → retryable `model_unavailable`; 413 and a 400 whose message says the prompt is too long → permanent `context_too_large`; other 4xx → permanent `model_config_error`; refusal → `model_refused`; anything else → retryable `internal_error`. SDK 1.10.0 has no stable `error_code` for an over-long prompt, so that case matches the message text; a miss only turns one permanent code into another. Tests build the real SDK error instances (`APIError.generate(status, body, ...)`) and drive the real client through a stubbed `fetch`, so the SDK's own status-to-class mapping is exercised.
- prepare-document (`src/jobs/prepareDocument.ts`) applies the final-state rule itself: a `ChunkingError` (`empty_after_parse`, `too_many_passages`) writes `failed` with its code and is rethrown as `UnrecoverableError` (one attempt); any other error is logged with its original text and writes `failed/preparation_error` (with a generic message) only when `job.attemptsMade + 1 >= job.opts.attempts`, otherwise the row stays `processing` and BullMQ retries (3 attempts, exponential backoff from 1 s). An integration test pins the BullMQ 6.7.7 semantics this relies on: `attemptsMade` is 0 on the first run and 1 on the second. If the failure write itself fails, the row stays in flight for the reconciler.
- Status writes are guarded in SQL (`ready`/`failed` only from `pending`/`processing`), and the final passages + `ready` write runs in one transaction behind `SELECT ... FOR UPDATE` on the document, so a stale or duplicate run can neither reopen a terminal row nor leave half the passages. Passages are replaced (delete + insert), so a rerun of an in-flight document gives the same spans. Finished jobs are kept (1 day / 7 days for failed) so the reconciler can tell "never enqueued" from "already ran".
- Passage cap `MAX_PASSAGES = 20,000` is a constant, not config: a 5 MB document packs into about 3,300 passages, so only pathological input (a heading every few words) hits it.
- Failure table for generate-answer (`attempts: 3`, exponential backoff from 1 s; one BullMQ attempt = one API call because the SDK runs with `maxRetries: 0`):

  | Cause | Code | Retried? | Row after the job |
  |---|---|---|---|
  | 429, 5xx, 529 overloaded, connection error, our `MODEL_TIMEOUT_MS`, retryable mid-stream `event: error` | `model_unavailable` | yes, up to 3 attempts | `pending` between attempts; `failed` after the 3rd |
  | 400 "prompt is too long", 413 | `context_too_large` | no (`UnrecoverableError`) | `failed` after 1 attempt |
  | other 400, 401, 403, 404, 422 | `model_config_error` | no | `failed` after 1 attempt |
  | `stop_reason: 'refusal'` | `model_refused` | no | `failed` after 1 attempt |
  | `stop_reason: 'max_tokens'` with ≥ 1 verified citation | none | n/a | `completed`, `finishReason: 'max_tokens'` |
  | `stop_reason: 'max_tokens'` with no verified citation | `answer_truncated` | no | `failed` after 1 attempt (not reported as "not in the document") |
  | no verified citation and no `NOT_IN_DOCUMENT:` marker (uncited reply, or every citation dropped) | `citations_unverified` (warn log with drop reasons) | no | `failed` after 1 attempt (not reported as "not in the document") |
  | missing question / document not ready | `internal_error` | no | `failed` |
  | any other exception (bug, DB hiccup) | `internal_error` (generic message, details logged) | yes | `failed` after the 3rd |
  | worker died mid-job (compose's `stop_grace_period` is 120 s, above `MODEL_TIMEOUT_MS`, so a normal stop lets jobs finish; `restart: unless-stopped` brings a crashed worker back, since the stalled-job rerun and the reconciler run only in a live worker) | BullMQ's stalled-job check moves it back to waiting (per BullMQ docs, not an attempt; past `maxStalledCount` BullMQ fails the job, which the reconciler turns into `stalled`); not exercised by a test here | | the rerun clears partial content first |
  | job failed or completed but the row is still in flight > 2 min | `stalled` (set by the reconciler) | no | `failed` |

  A `failed` answer has its partial content cleared (it was unverified model text), frees the conversation for the next question, and is left out of later history. A retryable failure before the last attempt moves the row back to `pending` with content cleared, so a polling client sees "waiting" during the backoff, not a frozen half answer. Not done yet: honouring `retry-after` on 429/529 (BullMQ's exponential backoff ignores it).
- Why the processor owns terminal state: only the processor knows, inside its `catch`, both the classified error and whether this is the last attempt (`job.attemptsMade + 1 >= job.opts.attempts`, with `attemptsMade` 0 on the first run on BullMQ 6.7.7, pinned by tests for both queues). It writes `failed` before rethrowing, so the row is terminal by the time BullMQ records the job as failed. Relying on `worker.on('failed')` instead would put the terminal write in an event handler that is fire-and-forget (BullMQ does not await it), runs after the job is already marked failed, and is lost if the process dies in between, leaving the conversation blocked by `one_inflight_answer`. The event is kept only for logging; the reconciler covers the case where the processor's own write fails.
- Reconciler (`src/jobs/reconciler.ts`, runs in the worker on start and every 60 s): in-flight rows (`documents` pending/processing, assistant `messages` pending/streaming) untouched for 2 min are checked against `queue.getJob(rowId)`: no job → enqueue (covers a lost request-path enqueue or a removed job); job `failed` → row `failed/stalled` with a generic message (the job's `failedReason`, which can be raw internal error text, is only logged); job `completed` with the row still in flight → `failed/stalled`; active/waiting/delayed/prioritized → left alone. An active answer stays fresh because partial writes bump `updated_at`. Writes are the same SQL-guarded transitions as the processors use, so a job finishing at the same moment cannot be overwritten (tested: a row failed while the model is still generating stays failed, and the processor reports `superseded`). Passes never overlap (`runOnce` shares a pass in progress), a row whose check throws is logged and skipped without aborting the pass, and a failed pass resolves `null` (unit-tested with stubs). The thresholds are options, so tests run it with aged rows instead of waiting. Polling Postgres was chosen over a transactional outbox: it is less code and also covers jobs that BullMQ lost or failed outside our processor.

## Alternatives considered
- **Model-written quotes + fuzzy matching** (ask for answer + quotes as JSON, then find each quote in the document): rejected. Models paraphrase "quotes"; fuzzy matching then either rejects good answers or accepts text that is not in the document, and the match offsets are a guess. With Citations over our own sentence blocks the model only points at blocks, and the quote is our own `content.slice`, so it is in the document by construction. Cost: we depend on the Citations response shape, which is unverified here (see [Grounding and citations](#grounding-and-citations)).
- **Whole document always**: simplest, and it is our `full` mode, but it has no answer for documents over the context budget.
- **Embeddings / vector search**: no Anthropic embeddings API; a second provider and `pgvector` for one-document Q&A was not worth it in 4 hours (see [Retrieval](#retrieval)).
- **Streaming the answer inline from `POST` (SSE on the request)**: ties the answer to one socket; a dropped connection or a worker retry loses it, and the model call would run in the request path. Rejected for a persisted job plus polling (SSE from a stream as a later addition).
- **Redis pub/sub for streaming**: no replay, and a subscriber that connects after the first deltas misses them. Redis Streams were chosen for the SSE design instead.
- **`worker.on('failed')` for terminal state**: fires on every failed attempt (not only the last), is not awaited, and does not cover stalled jobs. The processor owns terminal state instead (see [Failure handling](#failure-handling)).
- **Transactional outbox** for enqueueing: a reconciler that polls in-flight rows is less code here and also recovers jobs that were enqueued and then lost.
- **ORM**: the full-text search SQL is raw anyway, and four tables do not need one.
- **CommonMark parser for chunking**: we would still need the masking and trimming for exact sentence spans on top (see [Document preparation](#document-preparation-chunking)).

## AI use
- Tools: Claude Code. The design came from a Claude Code brainstorm session in which the human made each choice: Anthropic as the only provider (hence lexical retrieval); a persisted job with SSE and polling, later reduced to progressive polling with SSE as a stretch goal after the plan review, and SSE skipped after Task 14; Claude Citations over sentence blocks, over model-written quotes with fuzzy matching and over sending the whole document every time.
- The plan file was the task contract. Each task lists its files, checkboxes and tests. Agents mark checkboxes, record additions (➕) and blockers or unverified items (⚠️), and note actual time. An automated plan-review agent read the plan before any code was written and caught: BullMQ's worker `failed` event fires on every attempt, not only the final one, and stalled jobs bypass it (→ the processor owns terminal state); a reconciler re-adding an existing `jobId` is silently ignored by BullMQ (→ the reconciler checks job state first); double stemming in the OR tsquery (→ second pass with the `simple` config); passages with zero sentences would make the API return 400 (→ every passage has at least one sentence); and the plan was about 5 h (→ scope cuts).
- Delegation: implementation ran as sequential task subagents, one per plan task with a fresh context. Each had to write tests and pass `pnpm test` and `pnpm typecheck` before committing, and log what it did to a progress file. The orchestrator prompt (the `planning:exec` workflow) gave each agent one plan task, a fresh context, the plan and progress-file paths, and the validation commands; after the tasks, review agents (quality, implementation, testing, simplification, documentation) reviewed the whole diff, and a fix agent verified each finding against the code.
- Code review outcome: review phase 1 reported 57 findings (1 critical, 9 major, 47 minor). The critical one was real: the ATX-heading and table-separator regexes in chunking backtracked quadratically, so one upload with a long line could block a worker for hours. Also fixed: a `max_tokens` cut reported as "not in the document", NUL/surrogates in `title`/`question` giving a 500, internal error text exposed to clients, a too-short compose stop grace period, `text/plain` not being a 415, vacuous or order-dependent tests, and missing tests for the reconciler race, concurrent questions, enqueue failures on the conversation routes, `PartialWriter` and mid-stream SSE errors (222 → 252 tests). The fixes are in the commit `fix: address code review findings`; the progress log lists each finding as fixed or not, with the reason. Review phase 1 iteration 2 (5 major findings, all fixed, 252 → 255 tests): a reply whose citations were all dropped (or that cited nothing) was shown as "not in the document" (now `citations_unverified`); headings were unbounded and uncounted though copied into every passage and sent as titles (now capped and counted); the api and worker services had no restart policy (now `unless-stopped`).
- These documents were drafted by the Task 10 agent from the code, the plan and the manual-check notes, extended by the Task 11–13 agents, finalised in Task 14 and corrected after the code review.
- Agent rules: [CLAUDE.md](CLAUDE.md) grew during the run: Stack, Invariants, Database and Workflow came from Tasks 1–8 and were what the task agents worked under; the "Patterns (learned while building)" and "Agent environment" sections were written in Task 14 as a summary for future agents and were not given to Tasks 1–13 (Commands and Debugging were added after the code review). - How the work was checked: after Tasks 4–9 the orchestrator re-ran `pnpm typecheck` and `pnpm test` itself (180/180 passing, 13 files) instead of trusting the agents' reports. Unverified work had to be marked in the plan, not reported as done.

The defensive citation verification means a wrong assumption drops quotes (and fails the answer with `citations_unverified`) instead of showing wrong ones.

## Access control
Not implemented (one user). With authentication, each document gets an `owner_id` (or a `document_members(document_id, user_id, role)` table for shared workspaces). Conversations inherit access from their document, and messages from their conversation. Every route resolves the caller first and filters by it in the same query (`WHERE id = $1 AND owner_id = $2`), answering 404 rather than 403 so ids do not leak. Jobs carry only row ids and run as the system, so the worker needs no change. Retrieval is already scoped to one document id, so a question can never see another user's text.

## Scaling to many documents (optional)
Not built. Answering across a million documents changes retrieval, not grounding. Passage preparation stays per document in a horizontally scaled worker pool. Retrieval becomes two-stage: a corpus index (sharded lexical search such as OpenSearch, plus an ANN vector index, since vocabulary mismatch matters more across many authors) returns candidate passages from many documents, then a reranker picks the top few. Those go to Claude as custom-content documents titled with document title and section, so each citation still resolves to one document and offset range and is verified the same way. Access filters must apply inside the index query, not after it. Prepared passages and per-document prompt prefixes become cacheable.
